# C# WPF 与 HTML/WebView2 性能复测

日期：2026-11-11。本报告比较当前源码的客户端，不比较编程语言的理论性能。

结论：C# 专用提交量少约 65%～77%，隐藏后的客户端 CPU 接近零；HTML 在前台刷新时 CPU 更低。对当前产品，内存与后台待机是 C# 的优势，前台刷新仍有优化空间。

## 口径

- Windows 11 build 26200，本机 16 个物理核心、24 个逻辑处理器、31.7 GiB 内存。WPF 报告渲染级别 Tier 2。
- CPU 是客户端进程组在 30 秒内的累计 CPU 时间除以墙钟时间，再除以 24；表格取三轮中位数，不是峰值。
- 内存采用 Private Bytes 专用提交量，单位 MiB，不等同于任务管理器默认的物理内存列。工作集另列，跨进程汇总可能重复计算共享页。
- C# 包含 WPF 客户端进程；HTML 包含 Python 宿主及所有 WebView2 子进程。夹具服务、采样器、生产后台、受管项目、DWM 和 GPU 显存不计入。
- 使用真实生产窗口、网页资源、状态解析和轮询；跳过正式启动事件、单实例、托盘图标和真实后台启动，避免修改个人配置、开机自启或正在运行的项目。
- 两版均为 1440x900 窗口。C# 保留当前毛玻璃和阴影；HTML 使用当前 `ops` 主题。内容区因标题栏不同略有差异。
- 保留默认刷新频率：C# 5 秒，HTML 2 秒。此结果代表当前使用配置，不是相同刷新次数的纯渲染效率比较。
- 小数据：6 个虚构项目、4 个监听服务、3 个关注进程；压力数据：相同项目与关注进程、400 个服务，CPU/内存字段每两秒变化。
- 每个客户端、每种数据量各启动三次，交叉顺序为 WPF、HTML、HTML、WPF、WPF、HTML。就绪后预热 10 秒，前台采样 30 秒；隐藏窗口并稳定 3 秒，再采样 30 秒。
- “隐藏”使用各自窗口的 Hide 方法，模拟隐藏到托盘后的窗口状态，不代表操作系统冻结进程，也不等同于最小化。
- 就绪校验覆盖实际列表条数、窗口可见性、HTML 脚本错误、WPF 轮询状态；恢复窗口后检查状态请求重新发生。
- 测试期间不主动关闭用户已有应用，整机有其他负载；各阶段的整机负载中位数范围为 23.65%～40.1%。本结果不是空闲实验室或低配实机测试。

## 小数据结果

| 状态 | 客户端 | CPU / % | 专用提交 / MiB | 工作集总和 / MiB | 进程数 | 30 秒状态请求 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 前台 | C# WPF | 0.246 | 193.4 | 173.1 | 1 | 6 |
| 前台 | HTML/WebView2 | 0.051 | 552.9 | 498.8 | 7 | 16 |
| 隐藏 | C# WPF | 0.002 | 187.7 | 174.2 | 1 | 0 |
| 隐藏 | HTML/WebView2 | 0.098 | 537.2 | 506.2 | 7 | 15 |

小数据场景中 C# 专用提交量低约 65%，但前台 CPU 高于 HTML。C# 隐藏后停止界面轮询；HTML 的宿主窗口虽然隐藏，页面仍报告 `document.hidden=false`，因此继续轮询。这是本次实际观察到的行为，没有在夹具里强制改变页面可见性。

## 压力结果

| 状态 | 客户端 | CPU / % | 专用提交 / MiB | 工作集总和 / MiB | 进程数 | 30 秒状态请求 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 前台 | C# WPF | 0.489 | 168.1 | 170.3 | 1 | 6 |
| 前台 | HTML/WebView2 | 0.355 | 732.9 | 658.9 | 7 | 15 |
| 隐藏 | C# WPF | 0.002 | 172.5 | 172.5 | 1 | 0 |
| 隐藏 | HTML/WebView2 | 0.425 | 722.0 | 670.7 | 7 | 15 |

压力场景中 C# 专用提交量低约 77%。C# 前台 CPU 三轮为 0.379%、0.489%、0.685%；HTML 为 0.355%、0.226%、0.430%。在这台仍有其他负载的电脑上结果存在波动，因此不把中位数视为所有电脑上的固定占用。

换算为单核 CPU 口径，小数据前台 C# / HTML 分别为 5.91% / 1.23%；400 服务时分别为 11.73% / 8.51%。本机 24 线程的整机百分比会显得较小，不能直接套用到双核或四核电脑，也不能据此推算另一型号 CPU 的精确占用。

隐藏后的内存仍保留，不能把“CPU 接近零”解释为无资源占用。恢复窗口后两版均重新发出状态请求，12 次恢复检查均通过，最长观测等待约 2.04 秒；这只是请求恢复时间，不是完整画面就绪耗时。

## 可复跑方法

在仓库根目录运行：

```powershell
dotnet build csharp/LocalOpsWindows.Benchmarks/LocalOpsWindows.Benchmarks.csproj -c Release --artifacts-path tmp/resource-benchmark-build
python tools/benchmark_clients.py --host tmp/resource-benchmark-build/bin/LocalOpsWindows.Benchmarks/release/LocalOpsWindows.Benchmarks.exe
```

测试工具使用本机已有的 psutil 5.9.0、pywebview 6.2.1、Python 3.12.8 和 .NET 10，不增加产品依赖。`--smoke --warmup 2 --seconds 5` 只作夹具预检，其短时数据不用于正式结论。`--dataset small` / `large` 可单独复跑。

普通数据的已完成三轮保存在 `tmp/resource-benchmark-20261111-final/rounds.json`。该次运行在后续压力场景遇到 WebView2 子进程退出而中止，未完成的压力轮次不纳入结论。普通场景每次采样均验证 PID 集合保持不变，累计 CPU 差值有效。

修订后的采样器使用 Windows Job Objects 累计 CPU，包含采样期间已退出的子进程，避免仅汇总存活进程漏计时间；每个完整阶段落盘一次数据。Job 不设置资源限制，不修改客户端行为。

补测压力数据保存在 `tmp/resource-benchmark-20261111-large-final/`，包含 `results.json`、`rounds.json`、逐秒 `samples.csv` 和各轮就绪记录。该运行共 145 次状态请求、0 次写请求、0 个 404，所有列表条数、隐藏/恢复和脚本错误检查通过。

## 历史与限制

2026-11-09 的历史记录保留在 `RESOURCE_COMPARISON.md`。复核发现旧宿主没有解除正式 `Startup` 事件，可能干扰单实例或产生额外窗口，因此不使用旧数据计算此次优化百分比。

尚未测量两个正式安装包的整套资源、低配 Windows 10 电脑、GPU/显存、实际托盘线程、长日志滚动、连续数小时的内存增长。采样结束后补查时，原先的真实客户端及 Python 后台均已不在运行，因此没有附加生产后台运行样本，也未为测量重新启动个人项目。没有对用户真实项目执行启动、停止或修改配置。本次不发布安装包，不改变产品功能。
